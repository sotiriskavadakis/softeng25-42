# Software Requirements Specification (SRS)

# [Σύστημα Διαχείρισης Φόρτισης Ηλεκτρικών Οχημάτων]

## 1. Εισαγωγή
Η παρούσα έκθεση αποτελεί την Προδιαγραφή Απαιτήσεων Λογισμικού (*Software Requirements Specification – SRS*) για την ανάπτυξη μιας ολοκληρωμένης πλατφόρμας διαχείρισης δικτύου φορτιστών ηλεκτρικών οχημάτων και των συναφών υπηρεσιών που αυτό υποστηρίζει.

Στο πρώτο μέρος παρουσιάζονται οι κύριες απαιτήσεις του συστήματος και καθορίζεται το αναγκαίο πλαίσιο για την ορθή κατανόηση των λειτουργιών και προδιαγραφών που αναλύονται στις επόμενες ενότητες.

Το παρόν έγγραφο έχει συνταχθεί με βάση το διεθνές πρότυπο *ISO/IEC/IEEE 29148:2018*, το οποίο ορίζει τις αρχές και τις βέλτιστες πρακτικές για τη διατύπωση απαιτήσεων λογισμικού.

### 1.1 Σκοπός
[cite_start]Σκοπός του έργου είναι η ανάπτυξη μιας εφαρμογής λογισμικού για έναν συγκεκριμένο πάροχο σημείων φόρτισης ηλεκτρικών οχημάτων[cite: 14]. [cite_start]Η εφαρμογή θα επιτρέπει στους χρήστες ηλεκτρικών οχημάτων (πελάτες) να εντοπίζουν και να χρησιμοποιούν τους φορτιστές του δικτύου, να διαχειρίζονται τον λογαριασμό τους και τις πληρωμές, και να παρακολουθούν το ιστορικό των φορτίσεών τους[cite: 8, 9]. [cite_start]Παράλληλα, θα παρέχει στον πάροχο τα εργαλεία για τη διαχείριση του δικτύου του μέσω ειδικών λειτουργιών[cite: 11].

### 1.2 Πεδίο εφαρμογής
[cite_start]Το λογισμικό που θα αναπτυχθεί αφορά την εφαρμογή ενός παρόχου δικτύου φορτιστών[cite: 10]. [cite_start]Θα περιλαμβάνει ένα back-end υποσύστημα για τη διαχείριση δεδομένων και υπολογισμών [cite: 39][cite_start], μία προγραμματιστική διεπαφή REST API για επικοινωνία [cite: 40][cite_start], μία δικτυακή εφαρμογή (front-end) για τους πελάτες προσβάσιμη από desktop browser και smartphone [cite: 43][cite_start], και μία διεπαφή γραμμής εντολών (CLI) για τις διαχειριστικές λειτουργίες του παρόχου[cite: 41]. [cite_start]Το σύστημα θα μπορεί να επικοινωνεί με τρίτα συστήματα, όπως υπηρεσίες πληρωμών ή εφαρμογές συγκέντρωσης δεδομένων από πολλούς παρόχους[cite: 16, 32].

### 1.3 Επισκόπηση προϊόντος

#### 1.3.1 Προοπτική προϊόντος
[cite_start]Το προϊόν αποτελεί ένα αυτόνομο σύστημα διαχείρισης για έναν πάροχο φόρτισης, το οποίο εντάσσεται σε ένα ευρύτερο "οικοσύστημα" όπου κάθε λειτουργός δικτύου διαθέτει τη δική του ανεξάρτητη εφαρμογή[cite: 6, 7]. [cite_start]Το λογισμικό δεν σχετίζεται με κάποιο πραγματικό, υπάρχον σύστημα[cite: 12]. [cite_start]Θα πρέπει να είναι ικανό να αλληλεπιδρά με εξωτερικές υπηρεσίες, όπως συστήματα πληρωμών [cite: 16][cite_start], και να παρέχει δεδομένα κατάστασης των φορτιστών σε εξουσιοδοτημένες τρίτες εφαρμογές[cite: 32].

#### 1.3.2 Λειτουργίες προϊόντος
Οι βασικές λειτουργίες που θα υποστηρίζει η εφαρμογή είναι οι εξής:
* [cite_start]**Διαχείριση Λογαριασμού Πελάτη:** Ο πελάτης θα μπορεί να δημιουργεί λογαριασμό, καταχωρώντας τα στοιχεία του, επιλογές υπηρεσιών πληρωμής και προτιμήσεις χρήσης[cite: 17].
* [cite_start]**Αναζήτηση και Πλοήγηση:** Οι πελάτες θα μπορούν να βλέπουν σε χάρτη τους διαθέσιμους φορτιστές και τους τιμοκαταλόγους, μέσω της web ή smartphone εφαρμογής[cite: 19]. [cite_start]Θα υποστηρίζεται η δυνατότητα πλοήγησης προς έναν φορτιστή, είτε μέσω της εφαρμογής του παρόχου είτε μέσω τρίτων εφαρμογών (π.χ. Google Maps)[cite: 20].
* [cite_start]**Δέσμευση Φορτιστή:** Θα παρέχεται η δυνατότητα δέσμευσης ενός φορτιστή για προκαθορισμένο χρονικό διάστημα, εντός του οποίου μόνο ο συγκεκριμένος πελάτης θα μπορεί να ξεκινήσει τη φόρτιση[cite: 23, 24].
* [cite_start]**Διαχείριση Φόρτισης:** Στην αρχή κάθε φόρτισης (session), θα προ-δεσμεύεται ένα ποσό από την υπηρεσία πληρωμής του πελάτη[cite: 25]. [cite_start]Ο πελάτης θα μπορεί να παρακολουθεί την πρόοδο της φόρτισης από το smartphone του και να τη διακόψει ανά πάσα στιγμή[cite: 28, 29]. [cite_start]Η φόρτιση θα τερματίζεται αυτόματα με την πλήρωση της μπαταρίας ή την εξάντληση του προ-δεσμευμένου ποσού[cite: 27].
* [cite_start]**Δυναμική Τιμολόγηση:** Ο τιμοκατάλογος (€/kWh) θα μπορεί να μεταβάλλεται ανάλογα με παράγοντες όπως η τοποθεσία, η ισχύς φόρτισης, η ώρα και οι τιμές χονδρικής της ενέργειας[cite: 30].
* [cite_start]**Ιστορικό και Στατιστικά:** Οι πελάτες θα έχουν πρόσβαση σε αναλυτικά στοιχεία και λογαριασμούς για τους τελευταίους 6 μήνες, καθώς και σε συγκεντρωτικά στατιστικά για μεγαλύτερες περιόδους[cite: 31].
* [cite_start]**Λειτουργίες Παρόχου:** Θα υπάρχουν λειτουργίες αποκλειστικά για τον πάροχο, προσβάσιμες μέσω διεπαφής γραμμής εντολών (CLI)[cite: 15].

#### 1.3.3 Χαρακτηριστικά χρηστών
Οι χρήστες του συστήματος διακρίνονται σε δύο κύριες κατηγορίες:
1.  **Πελάτες (Χρήστες Ηλεκτρικών Οχημάτων):** Είναι οι τελικοί χρήστες που διαθέτουν ηλεκτρικό όχημα και χρησιμοποιούν την εφαρμογή web και smartphone για να εντοπίσουν, να δεσμεύσουν και να χρησιμοποιήσουν τους φορτιστές. [cite_start]Διατηρούν λογαριασμό στον πάροχο[cite: 8].
2.  **Πάροχος (Διαχειριστής Συστήματος):** Είναι ο λειτουργός του δικτύου φορτιστών. [cite_start]Χρησιμοποιεί τις ειδικές λειτουργίες της εφαρμογής, κυρίως μέσω της διεπαφής γραμμής εντολών (CLI), για τη διαχείριση του συστήματος[cite: 11, 15].

#### 1.3.4 Περιορισμοί
Η ανάπτυξη του λογισμικού υπόκειται στους παρακάτω τεχνικούς περιορισμούς:
* **Backend Stack:** Επιτρέπεται η χρήση Python (π.χ. Django, Flask) ή JavaScript (Node.js/Express). [cite_start]Άλλες τεχνολογίες (π.χ. Java, .NET) απαιτούν αιτιολογημένη έγκριση[cite: 51, 52].
* [cite_start]**Βάση Δεδομένων:** Το σύστημα διαχείρισης βάσης δεδομένων πρέπει να είναι ένα από τα: MySQL, MariaDB, PostgreSQL, ή Mongo[cite: 52].
* **Εργαλεία Μοντελοποίησης:** Είναι υποχρεωτική η χρήση του Visual Paradigm (CE ή Enterprise trial) για τη δημιουργία διαγραμμάτων UML. [cite_start]Δεν επιτρέπονται άλλα εργαλεία, ούτε η online έκδοση του Visual Paradigm[cite: 55, 56].
* [cite_start]**Εργαλεία Τεκμηρίωσης:** Το έγγραφο SRS πρέπει να παραχθεί με χρήση PlantUML & markdown ή μέσω της λειτουργίας αυτόματης παραγωγής του Visual Paradigm Enterprise trial[cite: 57].
* [cite_start]**Εργαλεία Διαχείρισης Έργου:** Είναι υποχρεωτική η χρήση του Github για τη διαχείριση του κώδικα και των εκδόσεων, και του GitHub Projects για τη διαχείριση των εργασιών του έργου[cite: 58, 59].
* [cite_start]**Χρήση ΑΙ:** Είναι υποχρεωτική η χρήση εργαλείων ΑΙ σε όλες τις φάσεις του κύκλου ζωής του λογισμικού, με καταγραφή και υποβολή των διαλόγων[cite: 60].

### 1.4 Ορισμοί
* [cite_start]**Λειτουργός/Πάροχος:** Η εταιρεία που κατέχει και διαχειρίζεται ένα δίκτυο φορτιστών ηλεκτρικών οχημάτων[cite: 5].
* [cite_start]**Πελάτης:** Ο χρήστης ηλεκτρικού οχήματος που δημιουργεί λογαριασμό και χρησιμοποιεί τις υπηρεσίες του παρόχου[cite: 8].
* [cite_start]**Session (Γεγονός Φόρτισης):** Μια πλήρης διαδικασία φόρτισης, από την ενεργοποίηση του φορτιστή από τον πελάτη έως τη διακοπή της[cite: 25].
* [cite_start]**CLI (Command Line Interface):** Διεπαφή γραμμής εντολών για την εκτέλεση λειτουργιών που αφορούν τον πάροχο[cite: 15].
* [cite_start]**REST API:** Προγραμματιστική διεπαφή για την επικοινωνία μεταξύ των υποσυστημάτων της εφαρμογής (π.χ. frontend και backend) και με τρίτα συστήματα[cite: 40].

## 3. Απαιτήσεις

### 3.1 Λειτουργίες
[cite_start][Αναλυτική περιγραφή των λειτουργικών απαιτήσεων και των περιπτώσεων χρήσης (use cases) θα προστεθεί σε αυτό το σημείο, σύμφωνα με τα παραδοτέα της ομάδας[cite: 37, 65].]

### 3.2 Απαιτήσεις απόδοσης
[Δεν καθορίζονται συγκεκριμένες απαιτήσεις απόδοσης στην εκφώνηση του έργου.]

### 3.3 Απαιτήσεις ευχρηστίας
[cite_start]Το front-end της εφαρμογής θα πρέπει να διαθέτει προσαρμοσμένη διεπαφή (responsive design) για την ορθή λειτουργία και εμφάνιση τόσο σε desktop browsers όσο και σε smartphones[cite: 43].

### 3.4 Απαιτήσεις διασύνδεσης
* [cite_start]Το σύστημα πρέπει να διασυνδέεται με υπηρεσίες πληρωμών για την προ-δέσμευση και χρέωση ποσών[cite: 9, 16, 25].
* [cite_start]Το σύστημα πρέπει να μπορεί να παρέχει δεδομένα για την κατάσταση των φορτιστών σε τρίτες, εξουσιοδοτημένες εφαρμογές[cite: 32].
* [cite_start]Η εφαρμογή smartphone θα πρέπει να μπορεί να καλεί τρίτες εφαρμογές πλοήγησης (π.χ. Google Maps) για τη δρομολόγηση του πελάτη σε έναν φορτιστή[cite: 20].
* [cite_start]Το back-end θα εκθέτει τις λειτουργίες του μέσω μίας προγραμματιστικής διεπαφής REST API[cite: 40].
* [cite_start]Η διεπαφή CLI θα αξιοποιεί, όπου αυτό έχει νόημα, το REST API[cite: 42].

### 3.5 Λογικές απαιτήσεις βάσης δεδομένων
Η βάση δεδομένων θα πρέπει να αποθηκεύει και να διαχειρίζεται πληροφορίες για:
* [cite_start]Λογαριασμούς πελατών (στοιχεία, προτιμήσεις, μέσα πληρωμής)[cite: 17].
* Δίκτυο φορτιστών (τοποθεσίες, τύποι, κατάσταση).
* [cite_start]Συναλλαγές φόρτισης (sessions), περιλαμβάνοντας κατανάλωση ενέργειας, διάρκεια και κόστος[cite: 29].
* [cite_start]Τιμοκαταλόγους, οι οποίοι μπορεί να είναι δυναμικοί[cite: 30].
* [cite_start]Ιστορικά και στατιστικά δεδομένα χρήσης για τουλάχιστον 6 μήνες[cite: 31].

### 3.6 Περιορισμοί σχεδίασης
[cite_start]Το λογισμικό θα αποτελείται από τα εξής διακριτά τμήματα: ένα back-end υποσύστημα, ένα REST API, μία διεπαφή CLI και μία δικτυακή εφαρμογή front-end[cite: 38]. [cite_start]Η αρχιτεκτονική του back-end είναι στην επιλογή της ομάδας ανάπτυξης[cite: 39]. [cite_start]Δεν απαιτείται η ανάπτυξη native εφαρμογής για smartphone[cite: 2419].

### 3.7 Χαρακτηριστικά του λογισμικού συστήματος
* [cite_start]**Αξιοπιστία:** Το σύστημα πρέπει να διαχειρίζεται με ασφάλεια τις συναλλαγές και να διασφαλίζει ότι μόνο εξουσιοδοτημένοι χρήστες μπορούν να ενεργοποιούν έναν δεσμευμένο φορτιστή[cite: 24].
* [cite_start]**Διαθεσιμότητα:** Οι χρήστες θα πρέπει να μπορούν να βλέπουν την κατάσταση των φορτιστών (διαθέσιμος/κατειλημμένος) σε πραγματικό χρόνο[cite: 19].
* **Συντηρησιμότητα:** Η αρχιτεκτονική σε διακριτά υποσυστήματα (backend, frontend, API, CLI) διευκολύνει τη συντήρηση και την επέκταση του λογισμικού.

### 3.8 Συμπληρωματικές πληροφορίες
[cite_start]Η αναγνώριση και εξειδίκευση των απαιτήσεων θα γίνει μέσω συζητήσεων στο μάθημα[cite: 35]. [cite_start]Κάθε ομάδα είναι ελεύθερη να κάνει δικές της παραδοχές, εφόσον δεν συγκρούονται με τις γενικές απαιτήσεις[cite: 36].

## 4. Επαλήθευση
Η επαλήθευση της υλοποίησης θα πραγματοποιηθεί μέσω ελέγχων (testing). [cite_start]Συγκεκριμένα, απαιτείται η δημιουργία functional tests για το API και scripts ελέγχου για τη διεπαφή CLI[cite: 65].

## 5. Παραρτήματα

### 5.1 Παραδοχές και εξαρτήσεις
* **Παραδοχή:** Οι χρήστες (πελάτες) διαθέτουν smartphone ή πρόσβαση σε desktop browser για τη χρήση της εφαρμογής.
* **Εξάρτηση:** Το σύστημα εξαρτάται από τη διαθεσιμότητα εξωτερικών υπηρεσιών πληρωμών για την εκτέλεση χρεώσεων.
* **Εξάρτηση:** Για τη λειτουργία πλοήγησης, η εφαρμογή εξαρτάται από την ύπαρξη και τη σωστή λειτουργία τρίτων εφαρμογών χαρτών στο smartphone του χρήστη.

### 5.2 Ακρωνύμια και συντομογραφίες
* **SRS:** Software Requirements Specification (Προδιαγραφή Απαιτήσεων Λογισμικού)
* **CLI:** Command Line Interface (Διεπαφή Γραμμής Εντολών)
* **API:** Application Programming Interface (Προγραμματιστική Διεπαφή Εφαρμογών)
* **UML:** Unified Modeling Language (Ενοποιημένη Γλώσσα Μοντελοποίησης)
* **kWh:** Kilowatt-hour (Κιλοβατώρα)
